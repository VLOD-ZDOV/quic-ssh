# quic-ssh (qsh)

[English](README.md) | **Русский**

[![CI](https://github.com/VLOD-ZDOV/quic-ssh/actions/workflows/ci.yml/badge.svg)](https://github.com/VLOD-ZDOV/quic-ssh/actions/workflows/ci.yml)

`qsh` — замена `ssh`, которая работает поверх **QUIC (UDP)**. Если UDP не проходит, она сама переключается на **TLS поверх TCP**. Сервер называется `qshd`, он слушает один и тот же порт (по умолчанию **4422**) по UDP и TCP.

Чем QUIC лучше:

- **быстрее подключается:** на канале с RTT 50 мс команда выполняется в 3 раза быстрее, чем через ssh (см. [бенчмарки](#бенчмарки));
- **лучше держится на плохой сети:** используется congestion control BBR, при потерях пакетов (Wi-Fi, мобильная связь) скорость падает меньше;
- **каналы не мешают друг другу:** у каждой сессии, проброса порта и копирования свой поток, поэтому медленный `cp` не тормозит терминал (нет head-of-line blocking);
- **переживает смену адреса клиента** (NAT rebinding);
- **встроенный keep-alive.**

Что умеет:

- интерактивный shell с PTY, сменой размера окна и кодом выхода;
- выполнение команд (`qsh host cmd`) с stdin/stdout/stderr;
- локальный проброс портов `-L`;
- копирование файлов `qsh cp`;
- вход только по ключам Ed25519 (существующий `~/.ssh/id_ed25519` подходит);
- сопряжение по одноразовому коду без ручного копирования ключей.

## Установка

### Готовые бинарники

Статические сборки для Linux x86_64 и aarch64 лежат на странице [Releases](https://github.com/VLOD-ZDOV/quic-ssh/releases):

```sh
ARCH=$(uname -m)   # x86_64 или aarch64
curl -fsSL https://github.com/VLOD-ZDOV/quic-ssh/releases/latest/download/qsh-$ARCH-linux.tar.gz | tar xz
sudo install -m755 qsh-$ARCH-linux/qsh qsh-$ARCH-linux/qshd /usr/local/bin/
```

Один и тот же архив подходит и для клиента, и для сервера. Контрольные суммы лежат в `SHA256SUMS`.

### Из исходников

Нужен актуальный stable Rust. Сторонние C-библиотеки не нужны.

```sh
git clone https://github.com/VLOD-ZDOV/quic-ssh && cd quic-ssh
cargo build --release          # target/release/qsh и target/release/qshd
sudo install -m755 target/release/qsh target/release/qshd /usr/local/bin/
```

## Быстрый старт

**1. Сервер.** Откройте в фаерволе порт **4422 по UDP и TCP** и запустите:

```sh
sudo qshd                  # системный режим: могут входить все пользователи
# или просто
qshd                       # пользовательский режим: входить можно только под этим пользователем
```

При первом запуске создаётся ключ хоста и выводится его отпечаток.

**2. Сопряжение.** На сервере под тем пользователем, под которым будете входить:

```sh
qshd pair
# Pairing code: k7f3-9qxm  (single use, valid 10 minutes)
# On the client run:
#   qsh pair user@server k7f3-9qxm
```

На клиенте:

```sh
qsh pair user@server k7f3-9qxm
```

`pair` добавляет ключ клиента на сервер (`~/.config/qsh/authorized_keys`) и запоминает ключ сервера на клиенте (`~/.config/qsh/known_hosts`). Если у клиента ещё нет ключа, он создаётся в `~/.config/qsh/id_ed25519`.

**3. Вход.**

```sh
qsh user@server
```

Сопряжение можно пропустить: если ваш ключ уже есть в `~/.ssh/authorized_keys` на сервере (например, после `ssh-copy-id`), `qsh` его примет. При первом подключении он покажет отпечаток хоста, как ssh.

### Запуск как службы

```sh
# системный режим
sudo cp contrib/qshd.service /etc/systemd/system/
sudo systemctl enable --now qshd

# пользовательский режим (без root)
mkdir -p ~/.config/systemd/user
cp contrib/qshd-user.service ~/.config/systemd/user/qshd.service
systemctl --user enable --now qshd
loginctl enable-linger "$USER"     # чтобы работал и без активной сессии
```

Юниты лежат в `contrib/` в репозитории и в архиве релиза.

## Использование

```sh
qsh user@host                          # интерактивный shell
qsh user@host uname -a                 # команда
qsh -t user@host htop                  # команда с принудительным PTY
qsh -L 8080:localhost:80 user@host     # проброс порта (+ shell)
qsh -N -L 5432:db.internal:5432 host   # только проброс
qsh cp file.txt user@host:dir/         # загрузить
qsh cp user@host:logs/app.log .        # скачать
qsh -p 2222 user@host                  # другой порт (или user@host:2222)
qsh --transport tcp user@host          # принудительно TCP (или quic)
qsh -v user@host                       # покажет, какой транспорт выбран
qsh keygen                             # создать ~/.config/qsh/id_ed25519
```

Ключ клиента выбирается так: `-i FILE`, иначе `~/.ssh/id_ed25519`, иначе `~/.config/qsh/id_ed25519`. Зашифрованный ключ спросит пароль.

## Настройка сервера

| Режим | Запуск | Кто может войти | Файлы |
|---|---|---|---|
| системный | от root | любой пользователь (по своим ключам) | `/etc/qsh/config.toml`, `/etc/qsh/host_ed25519` |
| пользовательский | от обычного пользователя | только этот пользователь | `~/.config/qsh/qshd.toml`, `~/.config/qsh/host_ed25519` |

Конфиг необязателен. Ниже значения по умолчанию:

```toml
listen = "[::]:4422"            # UDP и TCP; если IPv6 выключен, используется 0.0.0.0
# host_key = "/etc/qsh/host_ed25519"
use_ssh_authorized_keys = true  # принимать и ~/.ssh/authorized_keys
allow_tcp_forwarding = true
max_connections = 256
```

Ключи пользователя хранятся в `~/.config/qsh/authorized_keys` и (если включено) в `~/.ssh/authorized_keys`. Учитываются только строки `ssh-ed25519`. Строки с опциями (`from=`, `command=` и т. п.) **игнорируются**, потому что qsh не умеет соблюдать эти ограничения.

Логи пишутся в stderr (journald). Уровень задаётся переменной `QSHD_LOG`, например `QSHD_LOG=qsh=debug`.

## Бенчмарки

Сравнение с OpenSSH 10 (`ssh`/`scp` с настройками по умолчанию). Сеть эмулируется через `tc netem` на loopback в отдельном network namespace (MTU 1500). Обе стороны работают на одной машине.

**Подключение и выполнение `true`** (медиана из 10 запусков):

| Сеть | ssh | qsh (QUIC) | qsh (TCP-фолбек) |
|---|---:|---:|---:|
| loopback, без задержки | 114 мс | 64 мс | 31 мс |
| RTT 50 мс, 100 Мбит/с | 665 мс | **214 мс** | 264 мс |
| RTT 100 мс, 1 % потерь, 20 Мбит/с | 1216 мс (худший 1516) | **364 мс** (худший 564) | 464 мс (худший 965) |

**Загрузка файла** (`scp` против `qsh cp`, медиана из 3 запусков):

| Сеть | Размер | scp | qsh (QUIC) | qsh (TCP-фолбек) |
|---|---:|---:|---:|---:|
| loopback, без задержки | 200 MiB | 5,3 Гбит/с | 4,6 Гбит/с | 10,2 Гбит/с |
| RTT 50 мс, 100 Мбит/с | 50 MiB | 64,8 Мбит/с | **85,2 Мбит/с** | 78,8 Мбит/с |
| RTT 100 мс, 1 % потерь, 20 Мбит/с | 10 MiB | 11,1 Мбит/с | **16,4 Мбит/с** | 13,7 Мбит/с |

Выводы:

- **Подключение** в 3 раза быстрее, чем через ssh, на любом канале с заметной задержкой. QUIC совмещает транспортный и TLS-хендшейк в 1 RTT, у ssh уходит несколько RTT на обмен версиями, KEX и аутентификацию.
- **При потерях** QUIC с BBR выдаёт почти всю полосу канала (16,4 из 20 Мбит/с), а scp — около половины.
- **На loopback** QUIC упирается в процессор (шифрование и UDP в userspace), поэтому там TCP быстрее. На реальных каналах ограничение в сети, а не в процессоре.

Воспроизвести (нужны только util-linux, iproute2 и OpenSSH, root не нужен):

```sh
cargo build --release
python3 bench/bench.py
```

## Безопасность

- **Шифрование** — только TLS 1.3 (rustls, ring), и на QUIC, и на TCP. Своей криптографии нет.
- **Сервер** предъявляет самоподписанный сертификат со своим ключом Ed25519. Клиент сверяет ключ с `known_hosts` (TOFU, как ssh). Если ключ изменился, соединение обрывается до отправки любых данных.
- **Клиент** входит через mutual TLS со своим ключом Ed25519. Подпись проверяется в рамках TLS-хендшейка, поэтому вход привязан к каналу. Паролей нет совсем.
- **Сопряжение** использует SPAKE2 по коду и подтверждение ключа, привязанное к TLS-сессии (exporter) и обоим ключам. Посредник (MITM) не может ни подобрать код офлайн, ни переслать доказательство. Код одноразовый (сгорает после первой попытки, даже неудачной) и живёт 10 минут.
- **Права**: в системном режиме процессы пользователя запускаются с его uid, gid и группами. Файловые операции (`cp`, запись authorized_keys при сопряжении) выполняет вспомогательный процесс `qshd` с правами пользователя, поэтому root не открывает файлы по путям, которыми управляет пользователь. authorized_keys и каталоги на пути к нему проверяются по правилам StrictModes.
- **Ограничения ресурсов**: таймаут хендшейка и приветствия, лимит соединений и потоков, idle timeout 60 с.
- **Обрыв соединения**: если клиент пропал, вся группа процессов сессии получает SIGHUP, а через 2 с SIGKILL. В отличие от ssh, команда без PTY не продолжает работать «в пустоту». При SIGINT/SIGTERM/SIGHUP клиент закрывает соединение корректно, и сервер узнаёт об этом сразу, не дожидаясь таймаута.

Проект молодой и не проходил внешний аудит. Для критичных систем держите обычный ssh как запасной вход.

## Ограничения

- Нет PAM, utmp/wtmp и `systemd-logind`-сессий (`loginctl` не увидит вход).
- Нет агент-форвардинга, X11, `-R` и рекурсивного `cp -r`.
- Только Linux/Unix.
