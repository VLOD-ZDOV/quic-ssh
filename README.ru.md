# quic-ssh (qsh)

[English](README.md) | **Русский**

[![CI](https://github.com/VLOD-ZDOV/quic-ssh/actions/workflows/ci.yml/badge.svg)](https://github.com/VLOD-ZDOV/quic-ssh/actions/workflows/ci.yml)

`qsh` — замена `ssh`, которая работает поверх **QUIC (UDP)**. Если UDP не проходит, она сама переключается на **TLS поверх TCP**: если QUIC не ответил за 0,7 с, параллельно пробуется TCP, и используется то, что подключится первым. Сервер называется `qshd`, он слушает один и тот же порт (по умолчанию **4422**) по UDP и TCP.

Чем QUIC лучше:

- **быстрее подключается:** на канале с RTT 50 мс команда выполняется в 3,4 раза быстрее, чем через ssh (см. [бенчмарки](#бенчмарки));
- **лучше держится на плохой сети:** используется congestion control BBR, при потерях пакетов (Wi-Fi, мобильная связь) скорость падает меньше;
- **каналы не мешают друг другу:** у каждой сессии, проброса порта и копирования свой поток, поэтому медленный `cp` не тормозит терминал (нет head-of-line blocking);
- **переживает смену адреса клиента** (NAT rebinding);
- **встроенный keep-alive.**

Что умеет:

- интерактивный shell с PTY, сменой размера окна и кодом выхода;
- выполнение команд (`qsh host cmd`) с stdin/stdout/stderr;
- пробросы: локальный (`-L`), обратный (`-R`), SOCKS-прокси (`-D`, `-R порт`), через stdio (`-W`), Unix-сокеты, X11 (`-X`/`-Y`), туннельные устройства (`-w`), через промежуточные хосты (`-J`) и `ProxyCommand`; добавляются и снимаются на лету через `~C` или `-O forward`/`-O cancel`;
- копирование файлов и каталогов (`qsh cp -r`); оборванное копирование файла при повторном запуске продолжается с места обрыва;
- те же опции командной строки, что у `ssh`, поэтому `sftp`, `scp`, `rsync`, `git` и `sshfs` могут работать через qsh;
- **сессии переживают обрыв сети:** после потери связи qsh сам переподключается, а shell остаётся на месте вместе с выводом, который ты пропустил;
- вход по любым SSH-ключам (Ed25519, ECDSA, RSA, аппаратные ключи), ssh-agent и его проброс (`-A`), пользовательские и хостовые сертификаты OpenSSH;
- одноразовые коды (TOTP) как второй фактор, встроенные, и пароли по желанию; PAM (`pam_access`, `pam_limits`, `pam_systemd`) в сборках с фичей `pam`;
- серверные настройки как в sshd: `allow_users`/`deny_users` и группы, `permit_root_login`, блоки `[[match]]`, `force_command`, `chroot_directory` со встроенным `internal-sftp`, баннер, motd, `~/.ssh/rc`, штрафы по адресам, `qshd -t`/`-T` и перечитывание по SIGHUP;
- сопряжение по одноразовому коду без ручного копирования ключей;
- алиасы хостов из твоего `~/.ssh/config` (`qsh myserver`).

## Установка

### Скрипт установки

Linux, macOS и Termux:

```sh
curl -fsSL https://github.com/VLOD-ZDOV/quic-ssh/releases/latest/download/install.sh | sh
```

Скрипт спросит, что ставить: только клиент (`qsh`) или клиент и сервер (`qsh` + `qshd`), а для сервера спросит, запускать ли qshd службой при загрузке (systemd, launchd или termux-services). Программы он кладёт в `/usr/local/bin` (попросит sudo), а если sudo нет, то в `~/.local/bin`, и сверяет скачанное с `SHA256SUMS`. Уже существующий файл службы он не трогает. Чтобы обойтись без вопросов: `... | sh -s -- --server --service` (или `--client`, `--no-service`). Ещё он спросит, держать ли одно соединение с хостом 10 минут (`ControlMaster`), чтобы одноразовый код вводился один раз, а следующие `qsh` и `qsh cp` шли без нового входа (`--share` / `--no-share`); сервер может ограничить это настройкой `totp_valid_for`. Для сервера он спросит ещё порт и режим одноразовых кодов: выключены, по желанию или обязательны (`--port 2222`, `--totp required`). Enter оставляет значение по умолчанию, `s` пропускает вопрос, а `--defaults` отключает остальные вопросы. Ответы записываются в конфиг, который создаёт qshd; всё прочее в нём остаётся закомментированным.

Windows (qsh и qshd), в PowerShell:

```powershell
irm https://github.com/VLOD-ZDOV/quic-ssh/releases/latest/download/install.ps1 | iex
```

Он ставит `qsh.exe` в `%LOCALAPPDATA%\Programs\qsh` и добавляет эту папку в `PATH`.

Потом для обновления запусти `qsh update`. Команда ставит последний релиз в ту же папку, обновляет и qshd, если он лежит рядом с qsh, и перезапускает работающую службу qshd. Перезапуск закрывает открытые на этом сервере qsh-сессии, поэтому в терминале скрипт сначала спрашивает; tmux, screen и задачи `nohup` с файлами служб из `contrib/` продолжают работать (`KillMode=process`, как у sshd). `qsh update v1.0.2` ставит конкретный релиз. Скрипт берётся из последнего релиза, а не из ветки main.

### Готовые бинарники

Если хочешь поставить вручную: статические сборки для Linux x86_64 и aarch64 лежат на странице [Releases](https://github.com/VLOD-ZDOV/quic-ssh/releases):

```sh
ARCH=$(uname -m)   # x86_64 или aarch64
curl -fsSL https://github.com/VLOD-ZDOV/quic-ssh/releases/latest/download/qsh-$ARCH-linux.tar.gz | tar xz
sudo install -m755 qsh-$ARCH-linux/qsh qsh-$ARCH-linux/qshd /usr/local/bin/
```

Один и тот же архив подходит и для клиента, и для сервера. Контрольные суммы лежат в `SHA256SUMS`.

### macOS

Клиент и сервер для Apple Silicon (`aarch64`) и Intel (`x86_64`):

```sh
ARCH=$(uname -m | sed s/arm64/aarch64/)
curl -fsSL https://github.com/VLOD-ZDOV/quic-ssh/releases/latest/download/qsh-$ARCH-macos.tar.gz | tar xz
sudo install -m755 qsh-$ARCH-macos/qsh qsh-$ARCH-macos/qshd /usr/local/bin/
```

При скачивании через curl у бинарников нет флага карантина. Если скачиваешь браузером, сними его командой `xattr -d com.apple.quarantine qsh qshd`. Чтобы запускать qshd как службу, смотри `contrib/qshd.plist`. На macOS срок действия аккаунта не проверяется: базы shadow там нет.

### Windows

Клиент `qsh.exe` лежит в `qsh-x86_64-windows.zip`. Распакуй его в папку из `PATH`. qsh использует `%USERPROFILE%\.ssh` (ключи, `config`, отметки `known_hosts`) и `%USERPROFILE%\.config\qsh` и сам работает со службой агента OpenSSH для Windows (`ssh-agent`). Доступно всё, кроме `-f`. `--full` запускает `ssh.exe` и ждёт его завершения. Сборка под Windows новая и проверяется автоматически, но интерактивную работу с ней проверяли меньше, чем под Linux; если что-то не так, сообщи. В архиве есть и сервер `qshd.exe`, который обслуживает того пользователя Windows, от которого запущен (см. ниже).

**qshd на Windows (новый).** Запусти `qshd.exe` от того пользователя, под которым будут входить (автозапуск при входе: `schtasks /create /tn qshd /sc onlogon /tr "%LOCALAPPDATA%\Programs\qsh\qshd.exe"`), и открой в брандмауэре UDP и TCP 4422. Ключи лежат в `%USERPROFILE%\.config\qsh\authorized_keys`; `qshd pair`, `qshd keys` и `qshd totp` работают как на Linux. Команды выполняются в `cmd.exe` (другую оболочку задаёт `QSHD_SHELL`, например `pwsh.exe`), терминал работает через ConPTY. Копирование (с докачкой), пробросы `-L`/`-R`/`-D` и одноразовые коды работают. На Windows нет: других пользователей, паролей, sftp, проброса агента и X11, проброса Unix-сокетов, `chroot_directory` (вход, к которому он относится, отклоняется) и сессий, переживающих обрыв связи. Имя пользователя пишется так же, как у аккаунта, с теми же заглавными буквами. qshd не проверяет, кто ещё может писать в `authorized_keys`: других пользователей не пускают права самого профиля.

### Android (Termux)

Нативная сборка под Android (на bionic libc, поэтому DNS работает) лежит в релизах как `qsh-aarch64-android`:

```sh
pkg install curl
curl -fsSL https://github.com/VLOD-ZDOV/quic-ssh/releases/latest/download/qsh-aarch64-android.tar.gz | tar xz
install -m755 qsh-aarch64-android/qsh qsh-aarch64-android/qshd $PREFIX/bin/
qsh pair user@server           # потом: qsh ui
```

Termux передаёт касания как клики мышью, поэтому `qsh ui` работает пальцем: тап по хосту выбирает его, повторный тап подключается.

### Из исходников

Нужен актуальный stable Rust. Сторонние C-библиотеки не нужны.

Для PAM в qshd (`use_pam`, Linux) собери с `cargo build --release --features pam`; для этого нужны файлы разработки libpam (`libpam0g-dev` в Debian и Ubuntu, `pam-devel` в Fedora). Бинарники релизов статические, PAM в них нет.

```sh
git clone https://github.com/VLOD-ZDOV/quic-ssh && cd quic-ssh
cargo build --release          # target/release/qsh и target/release/qshd
sudo install -m755 target/release/qsh target/release/qshd /usr/local/bin/
```

## Быстрый старт

**1. Сервер.** Откройте в фаерволе порт **4422 по UDP и TCP** и запустите:

```sh
sudo qshd                  # системный режим: могут входить все пользователи
# или просто
qshd                       # пользовательский режим: входить можно только под этим пользователем
```

При первом запуске создаётся ключ хоста и выводится его отпечаток.

**2. Сопряжение.** На сервере под тем пользователем, под которым будете входить:

```sh
qshd pair
# Pairing code: k7f3-9qxm  (single use, valid 10 minutes)
# On the client run this and type the code when asked:
#   qsh pair user@server
```

На клиенте:

```sh
qsh pair user@server
# Pairing code: k7f3-9qxm
```

Код спрашивается, а не передаётся в командной строке: там его, пока идёт сопряжение, могут прочитать другие пользователи клиентской машины. На машине, которой пользуешься только ты, можно и `qsh pair user@server CODE`.

**Уже есть доступ по ssh?** `qsh copy-id user@server` делает то же без кода, как ssh-copy-id: через твой ssh-вход добавляет ключ этого компьютера в authorized_keys qsh на сервере и читает ключ хоста qshd, который затем закрепляет (по пути его подлинность проверяет known_hosts самого ssh). qshd там должен быть установлен и запущен.

Для телефона `qshd pair --qr --host 203.0.113.10` дополнительно покажет команду QR-кодом: отсканируй его камерой и вставь текст в Termux. `--host` задаёт адрес в команде (по умолчанию — имя хоста сервера).

`pair` добавляет ключ клиента на сервер (`~/.config/qsh/authorized_keys`) и запоминает ключ сервера на клиенте (`~/.config/qsh/known_hosts`). Если у клиента ещё нет ключа, он создаётся в `~/.config/qsh/id_ed25519`.

**3. Вход.**

```sh
qsh user@server
```

Сопряжение можно пропустить: если ваш ключ уже есть в `~/.ssh/authorized_keys` на сервере (например, после `ssh-copy-id`), `qsh` его примет. При первом подключении он покажет отпечаток хоста, как ssh.

### Запуск как службы

Скрипт установки настроит это сам, если ответить «да». Вручную:

```sh
# системный режим
sudo cp contrib/qshd.service /etc/systemd/system/
sudo systemctl enable --now qshd

# пользовательский режим (без root)
mkdir -p ~/.config/systemd/user
cp contrib/qshd-user.service ~/.config/systemd/user/qshd.service
systemctl --user enable --now qshd
loginctl enable-linger "$USER"     # чтобы работал и без активной сессии
```

Юниты лежат в `contrib/` в репозитории и в архиве релиза.

## Использование

```sh
qsh user@host                          # интерактивный shell
qsh user@host uname -a                 # команда
qsh -t user@host htop                  # команда с принудительным PTY
qsh -L 8080:localhost:80 user@host     # проброс порта (+ shell)
qsh -N -L 5432:db.internal:5432 host   # только проброс
qsh -N -R 8080:localhost:3000 host     # обратный проброс: порт 8080 хоста -> твой порт 3000
qsh -N -D 1080 host                    # SOCKS4/5-прокси на localhost:1080
qsh -N -R 1080 host                    # SOCKS-прокси на сервере, подключения уходят отсюда
qsh -L /tmp/docker.sock:/var/run/docker.sock host   # Unix-сокеты с любой стороны -L/-R
qsh -J bastion user@internal           # через промежуточный хост (на обоих qshd)
qsh -f -N -L 5432:db:5432 host         # войти и уйти в фон
qsh -A host                            # пробросить ssh-agent
qsh -Y host xterm                      # проброс X11 (-X: недоверенный, как в ssh)
sudo qsh -w 0:0 -N root@host           # туннельные устройства tun0 <-> tun0 (root с обеих сторон)
sudo qsh -w any:3 -N alice@host        # не root: только созданное для него устройство (ip tuntap add tun3 mode tun user alice)
qsh cp file.txt user@host:dir/         # загрузить
qsh cp a.txt b.txt user@host:~/inbox   # несколько файлов в каталог (~ — домашний каталог)
qsh cp user@host:logs/app.log .        # скачать
qsh cp -r project/ user@host:src/      # скопировать каталог (в любую сторону)
qsh cp -C logs.txt host:               # со сжатием (zstd), для текста на медленном канале
qsh cp big.iso host:                   # оборвалось? запусти ещё раз — продолжит с места обрыва
qsh multi -g web -- uptime             # одна команда на нескольких хостах
qsh -p 2222 user@host                  # другой порт (или user@host:2222)
qsh --transport tcp user@host          # принудительно TCP (или quic)
qsh -v user@host                       # покажет, какой транспорт выбран
qsh -G myserver                        # показать итоговые настройки хоста
qsh keygen                             # создать ~/.config/qsh/id_ed25519 (или: qsh keygen FILE)
qsh --full myserver                    # режим совместимости с OpenSSH, см. ниже
qsh ui                                 # меню хостов со статусом и замером скорости
qsh -O check myserver                  # общее соединение (см. ниже)
qsh doctor myserver                    # не подключается? проверит каждый шаг и подскажет, что исправить
qsh -v myserver                        # каждый шаг подключения и входа, как ssh -v
qsh forget myserver                    # ключ хоста сменили намеренно: забыть его (как ssh-keygen -R)
qsh completions fish > ~/.config/fish/completions/qsh.fish   # Tab дополняет команды и хосты
                                       # bash: source <(qsh completions bash) в ~/.bashrc; zsh: то же с zsh
qsh update                             # поставить последний релиз (и qshd, если он рядом с qsh)
```

Опции работают как в `ssh`: их можно склеивать (`-tt`, `-NL…`), ставить после хоста и писать со значением слитно (`-p22`). Также поддерживаются `-l user`, `-o Key=value`, `-F configfile`, `-4`/`-6`, `-q`, `-n`, `-s` (подсистема), `-g` (пускать другие хосты на локальные пробросы), `-e` (escape-символ), `-T`/`-t`/`-tt`, `-b` и `-B` (локальный адрес или интерфейс, с которого идут подключения). Опции ssh, которые для qsh ничего не значат (шифры, MAC, обмен ключами, GSSAPI, `-C` и т. п.: qsh всегда использует TLS 1.3), принимаются и игнорируются (`-v` их перечислит); для копирования со сжатием есть `qsh cp -C`. Другие опции ssh, которые qsh не выполняет (`-E`, `-I`, `-o PubkeyAuthentication`, `-o VerifyHostKeyDNS`, `-o GatewayPorts`...), дают предупреждение после подключения qsh (кроме `-q`). `-Q`, `-o RevokedHostKeys`, `-o PermitRemoteOpen` и `-o RefuseConnection` отклоняются: без них qsh был бы менее строгим, чем просили. Так же отклоняется хост, в конфиге которого задан `RevokedHostKeys`, а при `PermitRemoteOpen` в конфиге — динамический `-R port`. Как и в ssh, неизвестный ключ `-o` — ошибка, если его не назвали в `-o IgnoreUnknown`. С `--full` qsh во всех этих случаях передаёт подключение ssh.

В сессии `~.` в начале строки разрывает соединение, даже если сервер уже не отвечает. `~C` открывает командную строку, чтобы добавить пробросы (`-L`, `-R`, `-D`) или снять их (`-KL`, `-KR`, `-KD`), `~#` показывает их список, `~^Z` приостанавливает qsh, `~?` показывает список escape-последовательностей, `~~` отправляет сам символ `~`.

### Ключи, ssh-agent и сертификаты

qsh входит теми же ключами, что и ssh, в таком порядке:

1. **Ключ TLS-хендшейка:** первый Ed25519-ключ из `-i`, `IdentityFile` в конфиге, `~/.ssh/id_ed25519` и `~/.config/qsh/id_ed25519`. Если сервер его принимает, вход не требует лишнего обмена.
2. **Иначе, как в ssh:**
   - сертификаты (`<ключ>-cert.pub`, `CertificateFile`);
   - ключи из ssh-agent (`SSH_AUTH_SOCK`, `IdentityAgent`; `IdentitiesOnly` учитывается);
   - файлы ключей любого типа: `-i`/`IdentityFile`, а по умолчанию `~/.ssh/id_rsa`, `id_ecdsa`, `id_ed25519`.

   Сначала qsh спрашивает сервер, какие ключи он примет, поэтому аппаратный ключ приходится трогать только для подходящего ключа. Подпись привязана к TLS-сессии.

Аппаратные ключи (`sk-ssh-ed25519`, `sk-ecdsa`) работают через ssh-agent (`ssh-add ~/.ssh/id_ed25519_sk`). Зашифрованный ключ спросит пароль. `SSH_ASKPASS` и `SSH_ASKPASS_REQUIRE` работают как в OpenSSH.

`-A` (или `ForwardAgent yes`) делает твой агент доступным на сервере через `SSH_AUTH_SOCK`. Сокет лежит в закрытом каталоге, который принадлежит тебе. Как и с ssh, root на сервере может пользоваться ключами агента, пока идёт сессия, поэтому пробрасывай его только на хосты, которым доверяешь (или используй `ProxyJump`). qsh не может привязать проброшенный агент к хостам (`session-bind` в OpenSSH требует SSH-сессии), поэтому ключи, добавленные через `ssh-add -h`, через него не работают: ssh-agent отказывает им в непривязанном соединении.

### Сессии, переживающие обрыв

Терминальная сессия (login shell или команда с `-t`) после потери связи хранится на сервере час:

- qsh замечает обрыв примерно за 15 с, сам переподключается и показывает вывод, который ты пропустил. Полноэкранные программы перерисовываются.
- Переход с Wi-Fi на мобильную сеть, сон ноутбука и короткие обрывы больше не убивают shell. По QUIC смена адреса (NAT rebinding) обычно вообще не требует переподключения.
- Нажатия во время обрыва теряются, а `~.` прекращает ожидание.
- Пока ты подключён, ничего не теряется: программа, которая пишет быстрее, чем терминал успевает показывать, ждёт его, как через ssh, а вставка любого размера доходит целиком. Пока тебя нет, хранится последний 1 МиБ вывода; программы продолжают работать, но та, что заваливает терминал выводом, притормаживается, а не занимает ядро процессора.
- До 16 таких сессий на пользователя. При достижении предела новая сессия закрывает ту, что дольше всех отключена (например, брошенную убитым клиентом).
- Обычный выход (exit, `~.`, закрытие терминала) завершает сессию на сервере, как раньше.
- Выключить можно через `PersistSession no` в `~/.config/qsh/config` (или `-o PersistSession=no`). Сессии с пробросом портов, агента или X11 не сохраняются; пробросы, добавленные позже через `~C`, заканчиваются вместе с потерянным соединением (qsh говорит, какие).
- После `^C` на экран досыпается не больше ~1 МиБ уже отправленного вывода (у ssh около 2 МиБ), во всех терминальных сессиях с qshd 1.0.5 и новее.
- `ServerAliveInterval` и `ServerAliveCountMax` задают, как быстро замечается мёртвое соединение. Для остальных сессий они работают как в ssh. qsh проверяет связь пингами в отдельных потоках, поэтому непрочитанный вывод или ввод, который удалённая команда пока не читает, не выдают живое соединение за мёртвое.

### Общее соединение (`ControlMaster`)

Как и ssh, qsh может держать одно соединение и запускать через него следующие сессии, команды и копирования на тот же хост — без нового рукопожатия и входа:

```
# ~/.config/qsh/config
Host *
    ControlMaster auto
    ControlPersist 10m
```

- `ControlMaster auto`: использовать работающий мастер или стать им. `yes` (или `-M`) — всегда становиться мастером. По умолчанию `no`: мастер используется, только если задан `ControlPath`.
- `ControlPersist 10m` оставляет мастер в фоне на 10 минут после последней сессии (`yes` — до `-O exit`); соединения через собственные пробросы мастера считаются сессиями. Без него мастером становится первый qsh и после своей сессии ждёт остальные.
- Сокет по умолчанию лежит в `~/.config/qsh/ctl/` (`ControlPath` или `-S путь`; подстановки `%h %p %r %C`). `ControlPath` из конфига ssh не используется: те сокеты говорят на протоколе ssh.
- `qsh -O check host`, `-O exit`, `-O stop`, `-O forward -L ...` и `-O cancel -L ...` — как в ssh.
- `-R` запуска идёт через мастер, и мастер снимает его, когда запуск заканчивается, как бы он ни закончился (у ssh такой проброс остаётся до конца мастера). Мастер, чья собственная сессия закончилась, снимает свои пробросы, прежде чем ждать остальных. Запуски с `-A` или `-X` открывают своё соединение. Терминальная сессия, начатая через мастер, переживает его: qsh сам входит заново и продолжает её. Мастер, чья собственная терминальная сессия переподключилась, продолжает делиться новым соединением.
- Не работает под Windows.

### Алиасы хостов (`~/.ssh/config`)

qsh читает твой `~/.ssh/config`, поэтому хосты, к которым ты уже ходишь по ssh, работают по имени:

```
# ~/.ssh/config
Host myserver
    HostName 203.0.113.10
    User root
    IdentityFile ~/.ssh/work_key
```

```sh
qsh myserver                        # = qsh -i ~/.ssh/work_key root@203.0.113.10
qsh cp backup.tar myserver:/srv/
```

Из `~/.ssh/config` qsh берёт `HostName`, `User` и `IdentityFile`. `Port` оттуда игнорируется, потому что это порт ssh. Для настроек qsh, включая порт, используй `~/.config/qsh/config` с тем же синтаксисом; его значения приоритетнее. qsh создаёт этот файл при первом запуске: все настройки в нём закомментированы на значениях по умолчанию, у каждой есть пояснение (шаблон: `contrib/qsh_config`). Существующий файл qsh не меняет:

```
# ~/.config/qsh/config
Host myserver
    Port 8080
```

Поддерживаются шаблоны `Host` (`*`, `?`, `!`), `HostName`, `User`, `Port`, `IdentityFile`, `LocalForward`, `RemoteForward`, `DynamicForward`, `RequestTTY`, `BatchMode`, `StrictHostKeyChecking`, `EscapeChar`, `AddressFamily`, `LogLevel`, `IdentitiesOnly`, `IdentityAgent`, `CertificateFile`, `ForwardAgent`, `ServerAliveInterval`, `ServerAliveCountMax`, `PersistSession` и `PredictiveEcho` (только qsh), `Compression` (для `qsh cp`), `ControlMaster`, `ControlPersist`, `ControlPath` (в `~/.config/qsh/config`), `ProxyJump` и `ProxyCommand` (в `~/.config/qsh/config`; тогда qsh работает через stdin/stdout программы, например `ProxyCommand qsh -W %h:%p bastion`), `SendEnv`, `SetEnv`, `RemoteCommand`, `SessionType`, `StdinNull`, `ForkAfterAuthentication`, `ExitOnForwardFailure`, `LocalCommand` вместе с `PermitLocalCommand`, `HostKeyAlias`, `ConnectTimeout`, `ConnectionAttempts`, `UserKnownHostsFile` и `GlobalKnownHostsFile` (по умолчанию `/etc/qsh/known_hosts`), `KnownHostsCommand` и `HashKnownHosts` (в `~/.config/qsh/config`), `AddKeysToAgent`, `PasswordAuthentication`, `NumberOfPasswordPrompts`, `ForwardX11`, `ForwardX11Trusted`, `ForwardX11Timeout`, `XAuthLocation`, `Tunnel`, `TunnelDevice`, `Tag` (или `-P`), `CanonicalizeHostname` с `CanonicalDomains`, `CanonicalizeMaxDots` и `CanonicalizeFallbackLocal`, `BindAddress`, `BindInterface`, `Include` и `Match` (`all`, `host`, `originalhost`, `user`, `localuser`, `exec`, `localnetwork`, `tagged`, `canonical`, `final`). Блок `Match` с условиями, которые qsh проверить не может (`version`…), не применяется, но `ProxyCommand` или `ProxyJump` в нём всё равно учитывается: qsh никогда не подключается в обход прокси, который может действовать. Записи known_hosts могут быть хэшированными (`ssh-keygen -H`) или шаблонами. Как и ssh, qsh читает `/etc/ssh/ssh_config` после `~/.ssh/config` (кроме случая с `-F`), `#` начинает комментарий в любом месте строки, а файлы конфигурации (и их Include), которые могут менять другие пользователи, не принимаются. Значения из командной строки (`user@`, `-l`, `:port`, `-p`, `-i`) всегда главнее; пользователя из командной строки видят и `Match user`, и `%r`.

### Режим совместимости с OpenSSH (`--full`)

С `--full` (включается сам, если qsh установлен как `ssh`) qsh работает как прозрачная замена `ssh`:

- Из `~/.ssh/config` берутся ещё и `Port` и `RequestTTY`. Без `--full` они относятся к ssh-сессии и игнорируются. `LocalForward`, `RemoteForward` и `DynamicForward` оттуда действуют в обоих случаях.
- qshd ищется **параллельно на порту ssh** (по умолчанию 22) **и на 4422**, используется тот, что ответил. На порту 22 qshd может работать только по UDP рядом с sshd (`tcp = false` в конфиге сервера). Если порт qsh задан явно (`-p`, `:port` или `Port` в `~/.config/qsh/config`), проверяется только он.
- Если qshd не ответил за 1 с или в `~/.ssh/config` для хоста задан `ProxyJump`/`ProxyCommand` (на промежуточных хостах может не быть qshd), запускается обычный **`ssh`** (или **`scp`** для `qsh --full cp`) с теми же аргументами. ssh сам применяет весь свой конфиг: агент, jump-хосты, свой known_hosts.
- Хосты без qshd запоминаются на час, чтобы следующие подключения сразу шли через ssh. `--transport quic` заставляет проверить заново.
- То, что qsh не может разобрать (`ssh -Q kex`, `-O forward`, имя пользователя вида `user@corp.example`), тоже уходит ssh. Для имени, которое знает только конфиг qsh (например, подключение, сохранённое в `qsh ui`), ssh получает его `HostName`, `User` и `IdentityFile`, чтобы попасть на тот же хост.
- При неверном ключе хоста или отказе во входе qsh на ssh не переключается. Хост, известный на одном порту-кандидате и предъявивший другой ключ на втором, тоже отвергается.

```sh
qsh --full myserver               # QUIC, если там есть qshd, иначе обычный ssh
qsh --full -v myserver            # покажет, что именно использовалось
```

### Инструменты OpenSSH поверх qsh

Программы, которые сами вызывают `ssh`, могут использовать qsh:

```sh
sftp -S qsh user@host                         # на сервере нужен sftp-server (пакет openssh-sftp-server)
scp -S qsh file.txt user@host:dir/
rsync -a -e qsh project/ user@host:src/
GIT_SSH_COMMAND=qsh git clone user@host:repo.git
sshfs -o ssh_command=qsh user@host:/srv /mnt/srv
```

Чтобы qsh использовали все программы, установи его как `ssh` раньше в `PATH`. Под именем `ssh` qsh включает `--full`, так что хосты без qshd по-прежнему открываются настоящим ssh:

```sh
ln -s "$(command -v qsh)" ~/.local/bin/ssh
```

### Хосты без открытого порта

Хост за NAT или там, где нельзя открыть порт, может держать туннель до любого доступного хоста с qshd:

```sh
# на скрытом хосте (от пользователя, под которым будете входить):
qsh -N -o ExitOnForwardFailure=yes -R 14422:127.0.0.1:4422 user@public.example.com
# откуда угодно:
qsh -J user@public.example.com you@localhost:14422
```

Сессия остаётся зашифрованной из конца в конец: публичный хост только передаёт байты, а ключ скрытого хоста проверяется как обычно. Порт на публичном хосте слушает только loopback. Чтобы туннель держался постоянно, используй `contrib/qsh-tunnel@.service` (пользовательский юнит systemd, инструкция внутри).

### Меню хостов и замер скорости (`qsh ui`, `qsh speed`)

`qsh ui` открывает меню подключений со всеми хостами из `~/.ssh/config`, `~/.config/qsh/config`, known_hosts и сохранённых в самом меню:

- **Статус:** у каждого хоста в фоне проверяется qshd (TLS-хендшейк с одноразовым ключом, без входа). В списке видно `● quic 42 ms`, `● tcp` (UDP заблокирован) или `○ ssh` (qshd нет), а также известен ли ключ хоста, новый он или изменился. Результаты кэшируются на 10 минут в `~/.config/qsh/ui-state.toml`, поэтому при повторном открытии меню серверы заново не опрашиваются; **`r`** проверяет все сразу.
- **Подключение:** **⏎ / тап** подключается (по умолчанию с `--full`, поэтому хосты без qshd открываются обычным ssh). После выхода из сессии возвращаешься в меню. Недавно использованные хосты поднимаются наверх.
- **Разовое подключение:** **`c`** подключается к `user@host[:port]` один раз, ничего не сохраняя.
- **Сохранённые подключения:**
  - **`n`** добавляет новое: имя, адрес, пользователь, порт, файл ключа, опции ssh, транспорт (auto/QUIC/TCP) и откат на ssh. В **ssh opts** пишутся обычные флаги ssh, например `-L 8080:localhost:80 -D 1080 -A -C` или `-o ServerAliveInterval=30`; они сохраняются строками конфига (`LocalForward` и т. д.) и передаются ssh, когда подключение идёт через него.
  - **`e`** меняет сохранённое подключение, **`d`** удаляет его.
  - Они хранятся в `~/.config/qsh/ui-hosts` (синтаксис ssh_config), поэтому `qsh ИМЯ` работает и из командной строки.
  - Твои собственные конфиги меню никогда не изменяет. Для хоста из них **`e`** меняет только настройки меню (транспорт, откат на ssh), а сохранить подключение с именем, которое уже есть у тебя в конфиге, нельзя.
- **История:** **`Tab`** показывает историю с результатом каждого подключения. **⏎** подключается снова, **`a`** сохраняет запись как подключение, **`d`** удаляет её.
- **Группы:** в форме **`e`** есть поле *groups* (например, `web prod`) — для любого хоста. Группы видны метками `#web`. **`/#web`** показывает ровно эту группу (просто `/web` найдёт имена, адреса и группы, где есть «web»), а **`x`** запускает одну команду на всех показанных хостах (`qsh multi`; без фильтра — на всех). Хранятся в `~/.config/qsh/groups`.
- **Замер скорости:** **`s`** запускает его со спидометром: задержка (5 пингов), затем 5 с скачивания и 5 с загрузки, со стрелкой и графиком в реальном времени.
- **Проброс портов:** **`f`** показывает пробросы хоста. **`a`** добавляет проброс: выбираешь, что он делает (открыть порт сервера здесь, открыть порт этой машины серверу или SOCKS-прокси), и вводишь порты; **`d`** удаляет; **`⏎`** подключается с ними, а **`t`** открывает только туннель, без оболочки. У сохранённого подключения пробросы запоминаются, для остальных хостов добавленные действуют только на следующее подключение.
- **Другие клавиши:** **`p`** выполняет сопряжение по коду из `qshd pair`, **`/`** включает фильтр, **`?`** показывает все клавиши (на узком экране в подсказке внизу помещаются не все), **`q`** выходит.
- **Экраны:** раскладка подстраивается под узкий экран телефона, работают мышь и касания (прокрутка, тап).

`qsh multi` запускает команду сразу на нескольких хостах: каждая строка вывода помечена хостом, в конце — список хостов, где не получилось:

```
$ qsh multi -g web db1 -- uptime
web1 | 10:21:07 up 12 days,  load average: 0.08, 0.03, 0.01
web2 | 10:21:07 up 40 days,  load average: 0.31, 0.25, 0.20
db1  | 10:21:07 up 3 days,  load average: 1.02, 0.97, 0.90
ok on all 3 hosts
```

Хосты обрабатываются параллельно (по умолчанию `-P 16`) в режиме `BatchMode`, поэтому ничего не может остановиться и задать вопрос: нужны ключи без запроса пароля (или агент) и хосты, уже записанные в known_hosts (или `--accept-new-host`). Слова после `--` склеиваются и выполняются удалённой оболочкой, как в ssh: `qsh multi -g web -- 'cd /srv && git pull'`. Код выхода — 0, если команда везде прошла успешно, 1, если где-то упала, и 255, если на каком-то хосте сбой самого qsh (не удалось подключиться или войти, либо команда сама вернула 255). С `--json` вывод приходит одним JSON-массивом в конце (`host`, `exit`, строки `stdout` и `stderr`) — для скриптов; `qsh doctor --json` делает то же для своих проверок.

`qsh speed host` делает тот же замер текстом:

```
$ qsh speed myserver
root@203.0.113.10:4422 over quic
ping          79.3 ms  (min 78.9, max 81.2)
download     107.2 Mbit/s  (64.0 MiB in 5.0 s)
upload        70.1 Mbit/s  (41.8 MiB in 5.0 s)
```

### Защита интервалов между нажатиями

В интерактивных сессиях qsh скрывает ритм набора от наблюдателя в сети, как `ObscureKeystrokeTiming` в OpenSSH:

- **Как работает:** пока ты печатаешь, пакеты уходят по фиксированным тактам каждые 20 мс и все одного размера. В тактах без данных отправляются поддельные нажатия («chaff»). Они продолжаются ещё случайные 1–2 с после остановки, а сервер отвечает на них как на настоящее эхо. Вставка текста и вывод команд не затрагиваются.
- **Зачем:** без этого интервалы между нажатиями видны в сети. Накопив много сессий, по ним можно сузить перебор паролей, набранных внутри сессии (`sudo`, `su`), и понять, какие команды набираются.
- **Цена (измерено):** нажатие доходит до сервера **в среднем на 10 мс позже, максимум на 20 мс**. Первое нажатие после паузы уходит сразу. Пока печатаешь, мелких пакетов примерно в 6 раз больше (≈50/с в каждую сторону, единицы КБ/с). В простое и при передаче данных цены нет.
- **Настройка:** `ObscureKeystrokeTiming no` или `ObscureKeystrokeTiming interval:40` в `~/.config/qsh/config` (или `~/.ssh/config`). Действует только на интерактивные сессии с PTY.

### Набор на медленном канале (предсказание эха)

Как mosh, qsh показывает набранное до того, как придёт эхо сервера, если эхо идёт дольше примерно 30 мс:

- qsh держит копию экрана в том виде, как его нарисовал сервер. Набранный символ рисуется у курсора, только если клетка пуста и только после того, как предыдущее нажатие в этой строке вернулось ровно таким, как предсказано.
- Enter, стрелки, Ctrl-комбинации и т.п. начинают отсчёт заново, как и любой вывод, вызванный не твоим набором (например, появившийся запрос): после запроса пароля ничего не показывается, пока сервер сам не вернёт символ, поэтому скрытый пароль на экран не попадёт. Неверное предсказание или эхо `*` от скрытого ввода ничего не подтверждает до следующего Enter или управляющей клавиши.
- Вывод, который эмулятор не моделирует (режим вставки, повтор символов, сохранение позиции курсора), приостанавливает предсказание до перерисовки экрана. Цветной фон и не-латинские символы не предсказываются.
- Если вывод сервера отличается, предсказанные символы стираются до его показа, так что экран всегда в итоге такой, каким его нарисовал сервер.
- `PredictiveEcho auto` (по умолчанию), `yes` (и на быстрых каналах) или `no` — в `~/.config/qsh/config` или через `-o`.

## Настройка сервера

| Режим | Запуск | Кто может войти | Файлы |
|---|---|---|---|
| системный | от root | любой пользователь (по своим ключам) | `/etc/qsh/config.toml`, `/etc/qsh/host_ed25519` |
| пользовательский | от обычного пользователя | только этот пользователь | `~/.config/qsh/qshd.toml`, `~/.config/qsh/host_ed25519` |

При первом запуске (или `qshd init`) qshd сам создаёт конфиг, где все настройки закомментированы со значениями по умолчанию (шаблон — `contrib/qshd.toml`): в `/etc/qsh` он читается всеми, как `sshd_config`, в пользовательском режиме закрыт. Существующий файл никогда не меняется. Настройки «да/нет» принимают `true`/`false`, `yes`/`no`, `on`/`off` или `1`/`0`. Все настройки со значениями по умолчанию:

```toml
listen = "[::]:4422"            # UDP и TCP; если IPv6 выключен, используется 0.0.0.0
# host_key = "/etc/qsh/host_ed25519"
use_ssh_authorized_keys = true  # принимать и ~/.ssh/authorized_keys
use_qsh_authorized_keys = true  # ~/.config/qsh/authorized_keys (false: только файлы ниже)
allow_tcp_forwarding = true     # или "no", "local" (только -L/-D/-W), "remote" (только -R)
max_connections = 256
max_startups = 64               # одновременно неаутентифицированных подключений (как MaxStartups у sshd)
max_startups_per_ip = 8         # ... с одного IP
connection_buffer_mb = 32       # на подключение: данные, которые программы ещё не прочитали. Обычно около 0;
                                # копится, когда проброс перестаёт читать (до 1/8 буфера на каждый), а когда буфер
                                # полон, ждёт всё подключение. RAM в худшем случае: max_connections × это
                                # (256 × 32 МиБ = 8 ГиБ), плюс до 256 КиБ на открытый поток через TCP.
                                # Маленькая VM: 8-16; нагруженный прокси: 64-256
session_scope = true            # от root под systemd: каждая сессия в своём scope в user-UID.slice, поэтому
                                # `systemctl status qshd` показывает сам qshd, а его перезапуск не трогает tmux
tcp = true                      # false: только UDP, например на порту 22 рядом с sshd для `qsh --full`
gateway_ports = "no"            # -R слушает только loopback; "yes": все адреса; "clientspecified"

max_auth_tries = 6              # неудачных подписей на соединение
allow_agent_forwarding = true
```

**SFTP и chroot.** В qshd есть встроенный SFTP-сервер `internal-sftp`, как в sshd: ему не нужна оболочка (он работает и для аккаунтов с `nologin`) и не нужны файлы внутри chroot. Его можно указать подсистемой `sftp` или в `force_command`, с опциями sshd `-R` (только чтение), `-u UMASK` и `-d DIR` (начальный каталог; `%u` пользователь, `%d` домашний каталог). Он же используется для `sftp`, если sftp-server из OpenSSH не установлен; тогда он запускается через оболочку пользователя, так что аккаунты с `nologin` и `git-shell` так SFTP не получат. Встроенным qshd запускает его только там, где его назвал сервер (подсистема, `force_command`, `command=` ключа); если клиент просит выполнить `internal-sftp`, это обычная команда для оболочки пользователя. `chroot_directory` запирает программы входа и его передачи `qsh cp` в каталоге; как и в sshd, сам каталог и все каталоги выше должны принадлежать root и никому больше не быть доступны на запись, иначе вход не удаётся. Классическая схема «только SFTP» — блок `[[match]]` выше.

Обратные пробросы (`-R`) слушают там, где разрешает `gateway_ports`; все, кроме root, не могут слушать порты ниже 1024. `allow_tcp_forwarding = false` выключает `-L`, `-R`, `-D` и `-W`.

**Проверка и перечитывание.** `qshd -t` проверяет конфиг и ключ хоста; `qshd -T` печатает действующие настройки, а `qshd -T -C user=alice,addr=192.0.2.7` — настройки для одного входа (с учётом `[[match]]` и того, можно ли пользователю войти вообще). По SIGHUP (`systemctl reload qshd`) qshd перечитывает конфиг: новые входы получают новые настройки, работающие сессии сохраняют свои. О сломанном конфиге пишется в лог, и остаётся старый. Изменения `listen`, `tcp`, ключа хоста, лимитов подключений, `session_timeout` и `client_alive_*` вступают в силу после перезапуска.

**Штрафы.** Как в sshd 9.8 и новее, адрес, с которого не удаётся войти, копит штрафное время (5 с за неудачный вход, 1 с за подключение без попытки входа, 10 с за превышение `login_grace_time`); когда наберётся 15 с, его новые подключения отбрасываются, пока время не выйдет (не дольше 10 минут). IPv6-адреса считаются по /64. Несуществующие пользователи и отказы в сопряжении считаются как неудачный вход, так что по штрафам не узнать, какие аккаунты есть.

Пользователи, которых не пускают `deny_users`/`allow_users`/`deny_groups`/`allow_groups` или `permit_root_login = "no"`, обрабатываются как несуществующие: они получают тот же ответ «access denied», так что по нему не узнать, какие аккаунты есть.

Ключи пользователя хранятся в `~/.config/qsh/authorized_keys` (если не задано `use_qsh_authorized_keys = false`) и (если включено) в `~/.ssh/authorized_keys`. Подходят все типы ключей, кроме DSA и RSA короче 2048 бит. Соблюдаются такие опции:

- `command=` (исходная команда попадает в `SSH_ORIGINAL_COMMAND`; передача файлов запрещается);
- `from=` (адреса и CIDR);
- `restrict`, `no-pty`/`pty`, `no-port-forwarding`/`port-forwarding`, `no-agent-forwarding`/`agent-forwarding`;
- `permitopen=`, `permitlisten=`, `expiry-time=`;
- `cert-authority` с `principals=`;
- `no-touch-required`, `verify-required`.

Строка с любой другой опцией **не используется вовсе**: ограничение, которое qsh не умеет соблюдать, никогда не превращается в доступ.

**Сертификаты.** Подпиши ключи командой `ssh-keygen -s ca -I id -n USER key.pub`, затем доверься CA на весь сервер (`trusted_user_ca_keys`) или для одного пользователя строкой `cert-authority`. `force-command`, `source-address` и расширения `permit-*` соблюдаются. Для сертификатов хоста подпиши его ключ (`ssh-keygen -s ca -I host -h -n host.example.com /etc/qsh/host_ed25519.pub`), а на клиентах добавь `@cert-authority *.example.com <ключ CA>` в `~/.config/qsh/known_hosts` или `~/.ssh/known_hosts`: хостам с действительным сертификатом доверяют без вопроса при первом подключении. Строки `@revoked` учитываются. Сертификаты без срока действия (`ssh-keygen` без `-V`) тоже работают. Как и в OpenSSH, хост, чей сертификат выдан отозванным CA или выдан доверенным CA, но просрочен или сделан для другого имени, не принимается, даже если его ключ есть в known_hosts.

**Ключи от программы.** `authorized_keys_command` работает как `AuthorizedKeysCommand` в sshd: вывод программы читается как файл authorized_keys, в дополнение к файлам. Подстановки: `%u` пользователь, `%h` домашний каталог, `%U` uid, а для предложенного ключа `%f` (отпечаток), `%k` (base64), `%t` (тип). С ключевой подстановкой программа запускается для каждого предложенного ключа. Путь к программе должен быть абсолютным, менять её может только root (в пользовательском режиме — root или пользователь сервера); лимит 10 с; под root она запускается только от `authorized_keys_command_user`.

**Отзыв ключей.** `revoked_keys` указывает файл с открытыми ключами (по одному в строке) или KRL, созданный `ssh-keygen -k`. В KRL можно отозвать и сертификаты по серийному номеру или ID ключа, и целиком CA. Файл читается при каждом входе, так что изменения действуют сразу. Если файл задан, но не читается, не принимается ни один ключ.

**Спаренные ключи.** `qshd keys` от имени пользователя на сервере показывает пронумерованный список ключей, которые могут входить через qsh (их добавляет `qsh pair`); `qshd keys --remove N` (или отпечаток) удаляет ключ, например потерянного или списанного устройства; ключ, записанный в нескольких строках или с опциями, удаляется из всех. Уже открытые с ним сессии работают до своего завершения. Ключи из `~/.ssh/authorized_keys` в этот список не входят (qshd читает их только при `use_ssh_authorized_keys`).

**Одноразовые коды (TOTP).** На сервере от имени пользователя выполни `qshd totp`. Команда покажет QR-код для любого приложения-аутентификатора и включит коды, когда ты введёшь один из них. Дальше при входе после ключа спрашивается код, и каждый код срабатывает только один раз, в том числе на разных qshd одного пользователя (другой порт, пользовательский qshd рядом с системным). `qshd totp --disable` выключает коды. С `totp = "required"` аккаунты без кодов войти не могут. При возобновлении оборвавшейся сессии код повторно не спрашивается. Сразу после запуска qshd коды, которые мог принять прежний процесс, не принимаются (до полутора минут), чтобы код, подсмотренный до перезапуска, нельзя было использовать повторно.

**PAM.** qshd, собранный с `--features pam` (см. [Из исходников](#из-исходников)), умеет работать через PAM, как sshd с `UsePAM`: задай `use_pam = true` и положи файл службы в `/etc/pam.d/qshd` (`contrib/qshd.pam` подходит для Debian и Ubuntu; в других системах начни с их `/etc/pam.d/sshd`; `pam_service` задаёт другое имя файла). Тогда:

- каждый вход, и по ключу тоже, проходит проверку аккаунта в PAM (`pam_nologin`, `pam_access`, `pam_time`, истёкшие аккаунты); при отказе клиент видит «access denied», а причина пишется в лог. Просроченный пароль вход по ключу не блокирует, как и без PAM;
- с `password_authentication` пароли проверяет PAM (`pam_authenticate`) вместо /etc/shadow, так что работают LDAP, SSSD и другие модули; их вопросы уходят клиенту, а просроченный пароль не принимается, потому что qshd не может предложить его сменить;
- в системном режиме программа каждой сессии (shell, команда, подсистема) запускается в PAM-сессии, открытой от root до переключения на пользователя, поэтому действуют `pam_limits`, `pam_env`, `pam_loginuid` и `pam_systemd` (сессия logind, `loginctl`, `XDG_RUNTIME_DIR`). Рядом с программой остаётся маленький процесс от root, который закрывает сессию, когда она заканчивается. С PAM `session_scope` не используется: сессию размещает `pam_systemd`. Копирование файлов и проброшенные соединения идут без PAM-сессии.

У аутентификации и у сессии разные PAM-хэндлы (хэндл сессии живёт в процессе, который запускает программу), поэтому учётные данные, которые модуль выдал при аутентификации (билет Kerberos), до сессии не доходят. `pam_motd` и `pam_lastlog` не нужны: qshd показывает это сам.

Логи пишутся в stderr (journald). Уровень задаётся переменной `QSHD_LOG`, например `QSHD_LOG=qsh=debug`.

Выводы:

- **Подключение** в 3–3,4 раза быстрее, чем через ssh, на любом канале с заметной задержкой. QUIC совмещает транспортный и TLS-хендшейк в 1 RTT, у ssh уходит несколько RTT на обмен версиями, KEX и аутентификацию.

## Безопасность

- **Шифрование** — только TLS 1.3 (rustls, ring), и на QUIC, и на TCP. Своей криптографии нет.
- **Сервер** предъявляет самоподписанный сертификат со своим ключом Ed25519. Клиент сверяет ключ с `known_hosts` (TOFU, как ssh). Если ключ изменился (или отозван, или сертификат хоста недействителен), рукопожатие обрывается раньше, чем клиент покажет свой ключ, так что подменивший сервер даже не узнает, кто подключается.
- **Клиент** входит через mutual TLS со своим ключом Ed25519 или после хендшейка подписью любым SSH-ключом либо сертификатом по данным, привязанным к TLS-сессии. В обоих случаях вход нельзя переслать в другое соединение. Незнакомому хосту клиент показывает свой ключ только после того, как хост принят (в рукопожатии участвует одноразовый ключ). Файлы закрытых ключей, которые могут читать другие пользователи, не используются, как и в OpenSSH. Пароли выключены, пока сервер не задаст `password_authentication` (системный режим на Linux; хэши yescrypt и SHA-crypt из /etc/shadow, проверяются после проверки ключа хоста, для несуществующих пользователей делается та же работа). Можно добавить второй фактор (TOTP).
- **Сопряжение** использует SPAKE2 по коду и подтверждение ключа, привязанное к TLS-сессии (exporter) и обоим ключам. Посредник (MITM) не может ни подобрать код офлайн, ни переслать доказательство. Код сопрягает одно устройство, допускает 3 попытки (опечатка его не тратит, а тому, кто знает только имя пользователя, чтобы его сжечь, нужно 3 неудачных входа) и живёт 10 минут.
- **Права**: в системном режиме процессы пользователя запускаются с его uid, gid и группами. Файловые операции (`cp`, запись authorized_keys при сопряжении) выполняет вспомогательный процесс `qshd` с правами пользователя, поэтому root не открывает файлы по путям, которыми управляет пользователь. Проброшенные соединения (`-L`, `-D`) тоже открывает такой процесс и передаёт их qshd, поэтому правила файрвола по пользователю (`iptables --uid-owner`) действуют. Как и в sshd, передача файлов и подсистемы (sftp) запускаются через login-shell пользователя, поэтому `nologin` или `git-shell` блокируют и их. authorized_keys и каталоги на пути к нему проверяются по правилам StrictModes, по реальному пути (если `~/.ssh` — симлинк, проверяется то место, куда он ведёт).
- **Ограничения ресурсов**: таймаут хендшейка и приветствия, лимит неаутентифицированных подключений всего и с одного IP (как MaxStartups), лимит соединений и потоков, idle timeout 60 с (на запасном TCP — TCP keepalive и предел в минуту на неподтверждённые данные). До входа соединение может открыть лишь несколько потоков, и сервер держит для него не больше ~1 МиБ. Поиск пользователей и чтение файлов ключей идут вне потоков, обслуживающих сеть, а помощники никогда не держат заблокированным pipe, который читает qshd.
- **Никаких унаследованных дескрипторов:** как `closefrom` в sshd, программа пользователя получает от qshd только stdin, stdout и stderr (никаких терминалов других сессий, даже на мгновение).
- **Копирование каталогов** (`cp -r`) распаковывает только обычные файлы и каталоги. Абсолютные пути, `..`, ссылки и файлы устройств отклоняются, биты setuid/setgid сбрасываются, поэтому вредоносный сервер не может записать ничего за пределами целевого каталога. Заголовки длинных имён и PAX больше 64 КиБ отвергаются до чтения, так что забить память клиента он тоже не может.
- **Проброс портов** в системном режиме подключается от имени пользователя, а не root, поэтому правила фаервола по uid работают. Аккаунты с истёкшим сроком действия (`chage -E`, `usermod -e`) не пускаются. Как и sshd на большинстве Linux-систем (с PAM), заблокированный пароль (`passwd -l`, `usermod -L`) не мешает входу по ключу: у многих аккаунтов, которые входят только по ключу, пароля тоже нет. Чтобы закрыть аккаунту вход, используй `usermod --expiredate 1 ИМЯ` или `deny_users`.
- **Обрыв соединения**: команда без терминала останавливается, когда клиент пропадает: вся группа процессов получает SIGHUP, а через 2 с SIGKILL. В отличие от ssh, она не продолжает работать «в пустоту». Терминальная сессия хранится `session_timeout`, чтобы клиент мог её возобновить; сделать это может только клиент того же пользователя со 128-битным токеном сессии. При SIGINT/SIGTERM/SIGHUP клиент завершает сессию и корректно закрывает соединение.
- **Безопасность памяти:** в qsh и qshd нет `unsafe`-кода (`#![forbid(unsafe_code)]`). Под root qshd переключается на пользователя во вспомогательном процессе (`qshd internal-become`): он выставляет группы, группу и пользователя и затем запускает программу пользователя.
- **Проброс агента** использует сокет в новом закрытом каталоге, принадлежащем пользователю. Подключения других пользователей отклоняются (проверка через `SO_PEERCRED`). Сокет удаляется, когда клиент отключается.

Все уязвимости из бюллетеней безопасности OpenSSH с 2006 года проверены на qsh. Каждая из них либо неприменима, либо покрыта тестом, воспроизводящим атаку, либо исправлена; подробности в [docs/openssh-cve-review.md](docs/openssh-cve-review.md). Зависимости проверяются `cargo audit` в CI.

Проект всё ещё молодой и не проходил внешний аудит. Для критичных систем держите обычный ssh как запасной вход.

## Ограничения

- PAM и сессии `systemd-logind` есть только в сборках с фичей `pam` и с `use_pam` (см. PAM в [настройке сервера](#настройка-сервера)); в бинарниках релизов PAM нет (вместо `pam_access` есть `allow_users`/`allow_groups`), и `loginctl` их входы не видит. Без них сессии всё равно получают `XDG_RUNTIME_DIR` и шину сессии, если есть `/run/user/UID` (другой вход пользователя или `loginctl enable-linger`), так что `systemctl --user` работает. 2FA встроена (TOTP). В системном режиме терминальные сессии записываются в utmp, wtmp и lastlog, если эти файлы есть (`who`, `last`); системы, перешедшие на wtmpdb, их не увидят.
- Аппаратные ключи только через ssh-agent; PKCS#11 в самом qsh нет (для него тоже используй агент).
- Как и со scp и sftp, файл запуска shell, который печатает текст в неинтерактивном режиме (например, `~/.zshenv`), ломает `qsh cp`.
- `-J` работает, только если на всех промежуточных хостах есть qshd (через другие хосты — `ProxyCommand ssh -W %h:%p bastion` в `~/.config/qsh/config` до TCP-порта qshd); с `--full` хосты с `ProxyJump`/`ProxyCommand` из конфига ssh отдаются ssh.
- Нет GSSAPI/Kerberos, PKCS#11 и FIDO-ключей без агента, `UpdateHostKeys`, `VerifyHostKeyDNS` и `CheckHostIP` (у qshd один ключ хоста, а записи known_hosts привязаны к имени).
- qshd на Windows новый; он обслуживает только пользователя, от которого запущен, без sftp, проброса агента и X11 и долгих сессий (см. раздел Windows выше).

### Обновление

`qsh update` ставит последний релиз. Если в заметках к релизу сказано обновить сначала qshd, начни с него.

qsh и qshd 1.0.5 работают со старыми версиями друг друга. Когда обе стороны 1.0.5, соединение через TCP может иметь до 512 потоков в каждую сторону (раньше 96), а `^C` быстро действует на экране (см. выше).

Тому, что v1.0 добавила в протокол (баннер, пароли, Unix-сокеты, X11, туннели), нужен qshd 1.0 на сервере; со старым qshd qsh сообщает, что возможность не поддерживается, а остальное работает. qsh 0.5 работает с qshd 0.4 и новее. Ключам, кроме Ed25519-ключа TLS, пробросу агента, одноразовым кодам, сертификатам хостов и сохраняемым сессиям нужен qshd 0.5. qsh 0.4 и 0.5 требуют как минимум qshd 0.4: более старые серверы отклоняют их с ошибкой «unsupported protocol version», поэтому сначала обнови qshd. qshd 0.5 по-прежнему принимает старых клиентов.
